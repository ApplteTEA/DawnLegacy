# 여명의 유산 — 게임 시스템 기획

## 확정: 플레이어 스타팅 룰렛
1. 플레이어가 게임에서 제공하는 17개 타입 중 하나를 선택한다.
2. 선택한 타입에 해당하는 스타팅 후보 풀을 구성한다.
3. 해당 풀에서 룰렛으로 포켓몬을 무작위 선택한다.
4. 확정한 포켓몬을 파티에 추가하고 저장한다.

타입 목록(현행 game.js): 노말, 불꽃, 물, 풀, 전기, 얼음, 격투, 독, 땅, 비행, 에스퍼, 벌레, 바위, 고스트, 드래곤, 악, 강철.

## 확정: 라이벌 스타팅 룰렛
1. 플레이어가 선택한 **타입**을 기준으로 상성상 유리한 라이벌 타입을 자동으로 결정한다.
2. 라이벌 타입에 해당하는 포켓몬 후보만 모은다.
3. 그 후보 중 포켓몬을 무작위로 선택한다.
4. 최초 확정된 라이벌 타입/종류를 저장하고, 이후 로드·재대결 때 재추첨하지 않는다.
5. 이후 라이벌의 스타팅은 동일 개체/진화 계열로 성장한다.

### 예시 (후보는 설명용이며 실제 DB와 검증 필요)
- 플레이어 불꽃 → 라이벌 물 → 리아코/꼬부기 등에서 룰렛
- 플레이어 물 → 라이벌 풀 → 치코리타/이상해씨 등에서 룰렛
- 플레이어 풀 → 라이벌 불꽃 → 브케인/파이리 등에서 룰렛

### 현재 구현한 17타입 대응표 (초기 정책, 세부 매핑은 조정 가능)

현재 `rival-system.js`는 플레이어가 **타입을 선택했을 때** 해당 타입에 공격이 효과가 굉장한 라이벌 타입을 우선 선택한다. 유리한 타입이 여러 개인 경우 아래 기본 우선순위를 사용한다. 이 대응표는 구현 기본값이며 사용자의 추가 기획에 따라 변경 가능하다.

| 플레이어 | 라이벌 | 플레이어 | 라이벌 |
| --- | --- | --- | --- |
| 노말 | 격투 | 불꽃 | 물 |
| 물 | 풀 | 풀 | 불꽃 |
| 전기 | 땅 | 얼음 | 불꽃 |
| 격투 | 비행 | 독 | 땅 |
| 땅 | 물 | 비행 | 전기 |
| 에스퍼 | 악 | 벌레 | 불꽃 |
| 바위 | 물 | 고스트 | 악 |
| 드래곤 | 얼음 | 악 | 격투 |
| 강철 | 불꽃 | | |

- 기존 플레이어 후보 산출 방식과 동일하게 기본형/비진화 종 및 해당 타입으로 진화하는 포켓몬을 후보에 포함한다.
- 선택한 타입의 실제 데이터 후보가 없을 때만 다른 유리한 타입을 탐색하고, 그마저 없으면 오류로 감지한다. 유리하지 않은 타입으로 조용히 대체하지 않는다.
- 라이벌이 받을 포켓몬은 위에서 선택된 타입의 후보 중 **균등 무작위**다. 가능하면 플레이어와 완전히 같은 종은 제외한다.
- 첫 결정 시 `s.rival={type, starter, level:5}`를 저장한다. 재로드하면 기존 값을 유지하고 재추첨하지 않는다.
- 기존 세이브 파일에 `rival`이 없고 플레이어 스타팅이 있으면, 최초 로드 시 단 한 번 생성해 기존 키 `dawnLegacyCompleteV2`에 저장한다. 기존 세이브 버전은 유지한다.
- 신규 시작: 플레이어 룰렛 결과 공개 → 라이벌의 유리한 타입/룰렛 결과 공개 → 필드 진입. 라이벌 룰렛 애니메이션은 이미 저장된 추첨 결과를 시각화할 뿐 결과를 다시 뽑지 않는다.
- 모험 기록에서 라이벌의 타입·포켓몬을 확인할 수 있다. **라이벌 NPC/실제 배틀/진화와 연동은 아직 미구현이다.**
- 17개 타입의 상성·후보 존재·추첨 결과·JSON 저장 가능 여부는 `tests/rival-system.test.cjs`에서 검사한다. Android 실기기 UI는 아직 확인하지 않았다.

### 아직 확정해야 할 상세 규칙
- 17개 타입 각각의 라이벌 대응 타입: 약점이 여러 개일 때 우선순위/무작위 여부
- **타입에 강하다**의 정확한 의미: 플레이어 선택 타입을 방어 타입으로 가정할 때 공격 기술이 효과가 굉장한지 기준으로 판정 권장
- 플레이어가 복합 타입 포켓몬을 뽑았을 때 선택 타입 기준 유지 vs 실제 포켓몬의 복합 방어 상성 재평가 (현재 합의는 **선택한 타입 기준**)
- 후보 풀이 비었을 때 처리: 조용히 임의 타입으로 바꾸지 말고, 후보를 보강하거나 기획 승인 후 대체 규칙 적용
- 복합 타입 후보 포함 기준: 후보의 주 타입만 vs 해당 타입을 포함하면 허용
- 룰렛 화면의 노출 방식, 시드/확률/중복 여부

### 구현 시 필수 테스트
- 17개 타입 전체에서 라이벌 후보 풀이 비지 않는지
- 플레이어 선택 타입에 대해 라이벌 타입의 공격 상성이 실제로 유리한지
- 저장 후 새로고침/재접속에도 라이벌 포켓몬이 유지되는지
- 이전 버전 저장 데이터에 라이벌 정보가 없어도 안전하게 처리되는지
- 라이벌 재대결 시 스타팅이 변경되지 않고 정상 성장하는지

## 체육관/배지 (제안)
8개 도시와 관장 타입은 STORY.md 초안을 따른다. 각 배지 획득에 따라 스토리 이벤트 플래그가 진행된다. 배지와 여명석의 직접 연결은 미확정이다.

## 스토리 이벤트 설계 (제안)
- 대화, 컷신, 전투, 보상, 퀘스트 상태를 분리한다.
- 이벤트는 최초 발생/진행/완료 플래그로 저장하고 중복 보상을 막는다.
- 특정 배지 수, 지역 입장, NPC 대화 등 명확한 트리거를 정의한다.
- 기존 세이브 데이터와 호환되는 이벤트 버전 관리가 필요하다.

## 배틀/포켓몬/그래픽
기존 게임 기능을 우선 보존한다. 포켓몬 종 데이터, 전투 상성, 필드 동행 렌더링은 서로 다른 시스템으로 취급한다. 배틀 스프라이트와 필드 스프라이트는 용도를 구분한다.

## 미구현/미검증 구분
이 문서는 **기획서**이며 코드 구현 완료를 의미하지 않는다. 실제 구현 상태는 PROJECT_STATUS.md와 CHANGELOG.md를 확인한다.
