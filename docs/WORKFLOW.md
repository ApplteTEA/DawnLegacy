# DawnLegacy — High / Work 개발 워크플로

> 적용일: 2026-11-04 · 프로젝트 운영 규칙 (게임 코드 구현 완료 여부와 별개)
> 공통 규칙: 루트 `AGENTS.md`. 인계 기록: `PROJECT_STATUS.md`, `CHANGELOG.md`.

## 1. 역할 분담

### GPT-6 High — 메인 개발
- 게임 구조, 신규 기능, 게임 콘텐츠, 시스템 로직, 스토리 이벤트 및 일반 버그 수정.
- 개발 전에 최신 GitHub 코드·관련 MD를 검토하고 범위를 정한다.
- 코드 및 기본 테스트 반영 후 `PROJECT_STATUS.md`, `CHANGELOG.md`, `TODO.md` 등을 갱신한다.
- 해결할 수 있는 결함은 즉시 수정한다. 복잡하거나 품질 개선이 필요한 사항은 `IMPROVEMENTS.md`에 등록한다.
- Work가 맡은 파일/기능은 같은 시점에 중복 변경하지 않는다.

### ChatGPT Work — 집중 개선 및 상세 검증
- 사용량이 확보된 시점에 누적 개선 과제를 우선순위대로 선택해 처리한다.
- 그래픽/UX 완성도, 구조 리팩터링, 시스템 연동, 재발하는 복잡한 버그, 정밀 테스트.
- Work라고 모든 문제를 한 번에 수행하지 않는다. 관련성 높은 과제 1~3개 또는 검증 가능한 한 묶음을 권장한다.
- 작업 전에 최신 GitHub 코드 및 **저장소의 모든 MD**를 확인한다. 과거 대화에서 읽은 문서도 재확인한다.
- 개선 후 코드/테스트/문서를 갱신하고 `IMPROVEMENTS.md`의 각 과제별 증거를 기록한다.

역할은 기본 원칙이다. 버그 난이도·사용량·진행 상황에 따라 담당을 변경할 수 있으나, **담당 변경은 문서에 기록**한다.

## 2. 기준 문서 및 단일 정보 원칙

| 파일 | 유일한 책임 |
| --- | --- |
| `AGENTS.md` | 모든 에이전트의 공통 규칙, 문서 읽기 의무 |
| `docs/WORKFLOW.md` | High·Work 역할과 Git/인계 운영 방식 |
| `docs/PROJECT_STATUS.md` | 최신 구현 현황 및 환경을 적은 검증 결과 |
| `docs/TODO.md` | **앞으로 개발할** 신규 기능·콘텐츠·시스템 계획 |
| `docs/IMPROVEMENTS.md` | **이미 있는 기능의** 버그·품질 저하·기술 부채·검증 결함 |
| `docs/CHANGELOG.md` | 날짜·변경 파일·커밋·테스트 결과에 대한 변경 기록 |
| `docs/ARCHITECTURE.md` | 실제 코드 구조·데이터 흐름·저장/렌더링/테스트 구조 |
| `docs/GAME_DESIGN.md` | 확정된 게임 규칙 및 구체적 설계 |
| `docs/WORLD_LORE.md`, `docs/STORY.md` | 세계관·스토리: 확정과 제안 구분 |

| `docs/STORY_EVENTS.md` | 승인 전 이벤트 ID, 대사, 트리거, 보상 및 안전 재진입 조건 |
| `docs/IMPLEMENTATION_PLAN.md` | 현재 프로토타입에서 완성형 8체육관 RPG로 이행하는 단계·의존성·마이그레이션 계획 |

- 한 과제의 본문은 TODO 또는 IMPROVEMENTS **한쪽에만** 둔다. 다른 문서에는 링크/ID만 기록한다.
- 문서에 없는 코드 변경, 변경된 코드에 반하는 문서가 있으면 소스와 테스트를 확인하고 문서를 정정한다.
- 사용자 승인을 받은 기획만 **확정**으로 표시한다. 나머지는 **제안**이다.

## 3. High 작업 루틴

1. GitHub 기본 브랜치 HEAD, `AGENTS.md`, `WORKFLOW.md`, 관련 MD와 소스 확인.
2. `TODO.md`의 한 작업 또는 명시적 사용자 요구사항 선택. 기존 기능 영향 범위 점검.
3. 작은 변경 단위로 구현. 저장 호환성·포획·전투·이동·NPC·모바일 조작 등 영향 기능 테스트.
4. 실제 수행한 검증만 기록. 브라우저 세로 뷰포트를 Android 실기기 테스트라 부르지 않는다.
5. GitHub 커밋 반영. `CHANGELOG.md`에 변경 사항/커밋, `PROJECT_STATUS.md`에 검증 결과, `TODO.md`에 완료 상태 반영.
6. 개선점은 `IMPROVEMENTS.md`에 ID·재현 방법·영향 파일·우선순위·완료 기준을 적는다. 심각한 기능 결함은 무조건 Work에 미루지 말고 개발 중단 여부를 판단한다.

## 4. Work 작업 루틴

1. 새 작업 시작 또는 사용량 제한 이후 재개 시 GitHub HEAD와 전체 MD를 다시 읽는다.
2. `IMPROVEMENTS.md`에 있는 작업의 상태·담당·완료 조건 확인. 이미 해결된 항목을 재구현하지 않는다.
3. 작업 범위가 큰 경우 별도 브랜치/PR 사용을 우선한다. 시작 시 기준 커밋 기록.
4. 개선·검증 후 실제 환경, 실패 항목, 미확인 사항, 변경 파일과 커밋 기록.
5. 변경 내용 통합 전 최신 기본 브랜치를 재확인한다. **이전 문서/코드를 통째로 덮어쓰지 말고** 신규 변경을 병합한다.
6. 과제별 상태를 업데이트한 뒤 High가 이어서 개발할 수 있도록 `PROJECT_STATUS.md`/ `CHANGELOG.md`에 인계 정보를 남긴다.

## 5. 진행 상태와 우선순위

- 상태: `제안` → `대기` → `진행 중` → `구현 완료(검증 대기)` → `검증 완료` → `종료`.
- 예외: `차단됨`, `보류`, `재발`. 검증 실패 시 `진행 중` 또는 `재발`로 되돌린다.
- P0: 진행 불가/데이터 손상/핵심 이동 장애. 우선 해결.
- P1: 플레이에 큰 영향 또는 반복되는 품질 문제.
- P2: 시각/UX 개선, 리팩터링 등 일반 개선.
- P3: 낮은 우선순위의 장기 개선.
- **요청을 제출한 것과 구현이 완료된 것은 다르다.** Work 사용량 제한으로 멈춘 작업은 `대기(Work 사용량 제한)`로 표시한다.

## 6. 커밋·충돌 방지·인계

- 기본 원칙: **동일 파일/기능에 대한 동시 작업 금지.** 부득이하면 서로 다른 브랜치/PR로 분리하고 충돌을 검토한다.
- Work가 작업 중이거나 대기 중인 범위는 High가 변경하기 전에 현황을 확인한다. 긴급 변경 시 Work가 재개할 때 확인할 수 있도록 기록한다.
- 문서만 업데이트할 때 게임 코드가 변경되지 않았음을 명확히 적는다.
- 큰 작업 완료 기준: GitHub 반영, 관련 테스트 결과, 회귀 확인, MD 최신화, 남은 문제 기록.
- 최신 커밋 SHA, 변경 파일, 검증 환경(PC 브라우저/실기기 등), 미해결 사항, 담당자를 인계에 포함한다.

## 7. 현재 예외 — 대기 중인 Work 요청

2026-11-04 기준 사용자로부터 **'필드 배경 개선 및 이동·충돌 시스템 전면 재구축'** Work 요청이 제출되었으나 사용량 제한으로 **대기 중**이라고 전달받았다.
- 작업 범위: 나무/건물/물/울타리·NPC 충돌, 순간이동 원인 제거, 공통 맵 데이터, 집·풀·나무·도로 픽셀아트 배경 개선, 관련 회귀 검증.
- 주인공/NPC/동행 포켓몬의 현재 필드 에셋·애니메이션은 보존한다.
- 현재 단계에서 **Work의 변경 커밋이나 검증 완료를 추정하지 않는다**. 실제 완료 후 `IMPROVEMENTS.md`와 `PROJECT_STATUS.md` 갱신.
- Work가 재개하면 이 문서와 새로 생성된 `IMPROVEMENTS.md`를 포함한 전체 MD를 재확인하고, 최신 코드를 기준으로 진행한다.
